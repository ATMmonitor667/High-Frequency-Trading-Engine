1. WHAT IS THIS PROJECT?
--------------------------------------------------------------------------------
A High-Frequency Trading (HFT) system is software that ingests live market data,
maintains its own view of the market (the order book), runs trading strategies
that decide when to buy/sell, and sends orders to an exchange - all in
microseconds. The whole game is LATENCY and CORRECTNESS under load.

You are building a self-contained simulation of this entire pipeline in C++.
Because you (probably) do not have a real exchange connection or colocation, you
will also build a small EXCHANGE SIMULATOR so your trading engine has something
real to talk to. This is exactly how professionals test before going live, and
it makes the project fully runnable on a laptop - which matters for demos.

The core data path you are building (the "hot path"):

   [Exchange Sim] --market data--> [Feed Handler] --> [Order Book]
        ^                                                   |
        |                                                   v
        |                                            [Strategy Engine]
        |                                                   |
        |                                                   v
        +---- orders / fills ----[Order Gateway]<----[Risk Checks]

Five things make it "HFT" and not just "a trading bot":
  1. A limit order book with price-time priority and O(1)/O(log n) operations.
  2. A matching engine that pairs buyers and sellers deterministically.
  3. Lock-free / wait-free data structures on the hot path (no mutex stalls).
  4. Cache-friendly memory layout + custom allocators (no malloc in hot path).
  5. Rigorous, reproducible latency benchmarking (you measure nanoseconds).

2. CORE CONCEPTS YOU MUST UNDERSTAND (the vocabulary)
--------------------------------------------------------------------------------
- LIMIT ORDER BOOK (LOB): the list of all resting buy orders (bids) and sell
  orders (asks), sorted by price. Best bid = highest buy. Best ask = lowest sell.
  The gap between them is the SPREAD.

- PRICE-TIME PRIORITY: orders match by best price first; ties broken by who
  arrived first (FIFO). Your engine must respect this exactly.

- ORDER TYPES (start with the first two): LIMIT, MARKET, then later CANCEL,
  MODIFY, IOC (immediate-or-cancel), FOK (fill-or-kill).

- MATCHING ENGINE: takes an incoming order and matches it against the opposite
  side of the book, generating TRADES (fills) and updating the book.

- MARKET DATA FEED: the stream of events (new order, cancel, trade) the exchange
  broadcasts. Your FEED HANDLER decodes it and updates your local book.

- TICK-TO-TRADE LATENCY: time from receiving a market data tick to sending your
  order. This is THE number HFT firms care about. You will measure it.

- LOCK-FREE QUEUE (SPSC ring buffer): how threads hand work to each other without
  locks. The single-producer/single-consumer ring buffer is your workhorse.

- BACKTESTING vs REPLAY: feed historical data through your system to evaluate a
  strategy's P&L offline before "going live" against the simulator.

3. SYSTEM ARCHITECTURE (the components, one folder each)
--------------------------------------------------------------------------------
common/        Core primitives reused everywhere: fixed-point Price type,
               timestamps (rdtsc / steady_clock), Order/Trade structs, enums,
               lock-free SPSC & MPSC ring buffers, memory pool allocator,
               branch hints (likely/unlikely), cache-line alignment helpers.

core/orderbook/        The limit order book data structure. Add/cancel/modify
                       orders; query best bid/ask and depth. This is the heart.

core/matching_engine/  Consumes orders, matches against the book, emits trades.
                       Deterministic, single-threaded hot loop.

marketdata/            Feed handler + decoders. Parses incoming messages (start
                       with a simple binary or JSON format, later a compact
                       binary protocol) into internal events.

network/               TCP/UDP transport. Start with plain sockets; later add
                       busy-polling, kernel-bypass concepts (io_uring), and
                       multicast for market data.

strategy/              Pluggable strategy interface + sample strategies:
                       market-making, mean-reversion, and a momentum/signal
                       strategy. Strategies see book updates, emit orders.

execution/order_gateway/  Sends orders out and handles acknowledgements/fills.

risk/                  Pre-trade risk checks: max position, max order size,
                       price collars, kill switch. Runs BEFORE every order.

logging/               Low-latency async logger (hot path only writes to a ring
                       buffer; a background thread does the I/O).

config/                Config loading (symbols, ports, risk limits, strategy
                       params) from a file so nothing is hard-coded.

apps/exchange_sim/     A standalone exchange simulator: accepts orders, runs a
                       matching engine, broadcasts market data. Your test venue.

apps/trading_engine/   The main binary: wires feed handler -> book -> strategy
                       -> risk -> gateway and runs the live loop.

apps/replay/           Replays recorded/historical data for backtesting.

benchmarks/            Microbenchmarks (Google Benchmark) for order book ops,
                       ring buffer throughput, and end-to-end tick-to-trade.

tests/                 Unit tests (order book correctness, matching rules) and
                       integration tests (engine vs simulator round trips).

5. END-TO-END BUILD PLAN (phased; each phase = a commit + a demo)
--------------------------------------------------------------------------------
Tooling baseline (set up once, Phase 0):
  - Language: C++20 (or C++23 if your compiler supports it). Compiler: GCC/Clang.
  - Build: CMake. Test: GoogleTest. Bench: Google Benchmark. Format: clang-format.
  - OS: Linux (HFT is Linux; use WSL2 if you are on Windows). Sanitizers: ASan,
    TSan, UBSan in debug builds. CI: GitHub Actions (build + test on every push).
  - Version control: git from commit #1. Small, frequent, well-described commits.

PHASE 0 - Foundations (week 1)
  Goal: a building, testing, CI-green skeleton.
  - Set up CMake, GoogleTest, Google Benchmark, clang-format, GitHub Actions.
  - Implement common/ primitives: a fixed-point Price (avoid floats for money),
    a Timestamp (wrap rdtsc and std::chrono), and Order/Trade/Side enums/structs.
  - Write your first unit tests (Price arithmetic, ordering).
  Demo: "make && ctest" passes; CI badge green on GitHub.

PHASE 1 - The Limit Order Book (weeks 2-3)  *** the heart ***
  Goal: a correct, fast single-threaded order book.
  - Data structure: map price-level -> FIFO queue of orders. Start with
    std::map for price levels (clear, O(log n)). Add/cancel/modify; best bid/ask.
  - Add an O(1) lookup from orderId -> location for fast cancels.
  - Heavy unit tests: price-time priority, partial fills, cancels, edge cases.
  Demo: feed a script of orders, print the book; tests prove correctness.
  Later optimization (revisit in Phase 8): replace std::map with a flat array of
  price levels indexed by ticks for cache-friendly O(1) access.

PHASE 2 - The Matching Engine (week 4)
  Goal: turn incoming orders into trades deterministically.
  - Implement matching: incoming aggressive order walks the opposite side,
    generating fills until filled or no more liquidity; remainder rests (LIMIT)
    or is dropped (IOC/MARKET).
  - Emit a Trade stream and updated book state.
  - Tests: known sequences -> known fills (build a golden-file test).
  Demo: order sequence in -> trades + final book out, matching by hand-check.

PHASE 3 - The Exchange Simulator (week 5)
  Goal: a venue your engine can talk to over the network.
  - apps/exchange_sim: wrap the matching engine behind a TCP/UDP server.
  - Define a simple wire protocol (binary struct first; document it).
  - It accepts orders and broadcasts market data (book/trade updates).
  Demo: telnet/netcat or a tiny client sends orders; sim responds with fills.

PHASE 4 - Market Data Feed Handler (week 6)
  Goal: consume the sim's feed and rebuild the book locally.
  - marketdata/feed_handler + decoders: parse wire messages into events.
  - Maintain a local mirror of the order book from the feed.
  - Verify your mirrored book matches the simulator's book exactly.
  Demo: run sim + feed handler; assert book consistency over thousands of msgs.

PHASE 5 - Strategy Engine + Risk + Gateway (weeks 7-8)
  Goal: close the loop - react to data and send orders.
  - strategy/: define an interface (onBookUpdate, onTrade -> emit orders).
    Implement a simple market-making strategy (quote both sides around mid) and
    a mean-reversion strategy.
  - risk/: pre-trade checks (max position, max order size, price collar, kill
    switch). Every order passes through risk before the gateway.
  - execution/order_gateway/: send orders to the sim, handle acks/fills, update
    positions and P&L.
  Demo: strategy trades against the sim; print running P&L and position.

PHASE 6 - Backtester / Replay (week 9)
  Goal: evaluate strategies offline on recorded data.
  - apps/replay: read recorded data from data/samples, feed it through the same
    strategy code path, produce P&L, Sharpe, max drawdown, fill stats.
  - Record real or synthetic data into data/samples (write a recorder in the
    feed handler).
  Demo: a backtest report (numbers + a simple equity-curve plot in docs/).

PHASE 7 - Low-Latency Concurrency (week 10)
  Goal: split into threads connected by lock-free queues; no locks on hot path.
  - common/ SPSC ring buffer between feed handler -> strategy -> gateway.
  - Pin threads to cores; busy-poll instead of sleeping on the hot path.
  - Async logger: hot path only enqueues; background thread writes.
  Demo: throughput and latency improve measurably vs Phase 5 (show before/after).

PHASE 8 - Optimization & Benchmarking (week 11)  *** the resume gold ***
  Goal: measure, then make it fast - with evidence.
  - benchmarks/: Google Benchmark for order book add/cancel/match and ring
    buffer throughput. Build an end-to-end tick-to-trade latency histogram
    (record timestamps; report p50/p99/p99.9 in nanoseconds).
  - Optimizations to try, each measured: flat-array order book, custom memory
    pool (no malloc on hot path), cache-line alignment + false-sharing fixes,
    branch hints, removing virtual calls on the hot path, prefetching.
  - Use perf, perf stat, and Linux perf counters; consider Intel VTune.
  Demo: a docs/PERFORMANCE.md with a latency table and flamegraphs. Numbers like
  "p99 tick-to-trade reduced from X us to Y us" are exactly what recruiters want.

PHASE 9 - Polish & Presentation (week 12)
  Goal: make it look like a product, not a homework assignment.
  - README.md with architecture diagram, build/run instructions, GIF/screenshot
    of it running, and the headline performance numbers up top.
  - docs/ARCHITECTURE.md with the design and trade-off discussion.
  - Clean code, consistent style, CI green, good test coverage.
  - Optional: a small live dashboard (book depth, P&L, latency) via a web UI.

6. THE EXTENSION FOLDER: CUDA + MACHINE LEARNING (optional, high-impact)
--------------------------------------------------------------------------------
Everything here lives under /extension and is built SEPARATELY from the core so
the core stays clean and dependency-free. Only start this after Phase 6+ works.

IMPORTANT REALITY CHECK (say this in your README - it shows maturity):
GPUs are NOT used for the ultra-low-latency hot path of real HFT, because the
CPU<->GPU transfer adds microseconds and GPUs are bad at branchy, single-event
logic. GPUs ARE used in trading for: (a) massively parallel BACKTESTING and
simulation, (b) TRAINING ML models, and (c) batch feature computation / research.
So position CUDA correctly - as research/backtest acceleration, not as "I put the
order book on a GPU." Knowing this distinction itself impresses interviewers.

6A. CUDA (extension/cuda/)
  Project ideas, easiest to hardest:
  1. GPU-accelerated backtesting: run thousands of strategy parameter
     combinations in parallel on historical data. This is the classic, legit
     "100x faster than CPU" win and is genuinely useful.
  2. Parallel Monte Carlo: price options or simulate many market scenarios.
  3. Parallel technical-indicator / feature computation across many symbols and
     time windows at once (feeds the ML side).
  Deliverable: a CPU vs GPU benchmark table in extension/docs (e.g., "swept
  10,000 parameter sets in N seconds on GPU vs M minutes on CPU").
  Skills shown: CUDA kernels, memory coalescing, host/device transfer, Thrust.

6B. MACHINE LEARNING (extension/ml/)
  Pipeline:
  1. features/: engineer features from the order book - order-book imbalance,
     micro-price, spread, recent trade flow, rolling volatility. (This is where
     most of the real edge and learning is.)
  2. training/: train a model to predict short-horizon price direction (next
     tick up/down) or mid-price move. Start simple: logistic regression / gradient
     boosting (XGBoost), then a small LSTM/MLP. Python + PyTorch is fine HERE.
  3. inference/: export the trained model (ONNX or TorchScript) and run inference
     from C++ using ONNX Runtime or LibTorch, so a strategy can call predict().
  4. Wire a "signal strategy" in the core strategy/ folder that uses the model's
     prediction (run it through the SAME risk checks and backtester).
  Deliverable: a backtest comparing the ML strategy vs the baseline strategies,
  with honest metrics (accuracy, P&L, Sharpe, drawdown) and a discussion of
  overfitting / look-ahead bias. Honesty about limitations reads as senior.
  Skills shown: feature engineering, model training, C++/ML integration, ONNX,
  realistic evaluation.

Suggested extension build order:
  E1. ML features from your recorded data (extension/ml/features).
  E2. Train + evaluate a baseline classifier offline (extension/ml/training).
  E3. Export model; run inference in C++ (extension/ml/inference); add signal
      strategy to the core and backtest it.
  E4. CUDA-accelerated parameter-sweep backtester (extension/cuda).
  E5. (Stretch) CUDA feature computation feeding the ML pipeline.

7. RECRUITER PLAYBOOK - HOW TO MAKE THIS IMPRESSIVE
--------------------------------------------------------------------------------
What HFT / quant recruiters actually look for (from research below): depth over
breadth, measurable results, low-level mastery, and evidence you can dig into a
hard problem. Translate that into concrete moves:

7A. Lead with NUMBERS. The single most powerful thing you can do.
  - "Limit order book sustaining N million operations/sec."
  - "p99 tick-to-trade latency of X microseconds (measured, histogram in repo)."
  - "Lock-free SPSC queue at Y million msgs/sec; reduced p99 latency by Z%."
  - "GPU parameter sweep: 10,000 backtests in N s vs M min on CPU (100x)."
  Put the top 3 numbers at the very top of the README.

7B. Show the LOW-LEVEL chops recruiters screen for:
  - Lock-free data structures, cache-line alignment / false-sharing fixes,
    custom memory pool (no malloc on hot path), branch prediction hints, reading
    assembly / perf counters for hot loops. Document each with a before/after.

7C. Make it RUNNABLE and VISIBLE:
  - One-command build and run (scripts/). A GIF or screenshot of it trading.
    Recruiters spend ~60 seconds on a repo - the README must sell it instantly.
  - Architecture diagram in the README. Clear, professional.

7D. Prove ENGINEERING MATURITY:
  - CI green badge, unit + integration tests, sanitizers, clang-format, clear
    commit history. This separates you from "it works on my machine" projects.

7E. Prove you understand the DOMAIN, not just code:
  - A docs/DESIGN.md discussing trade-offs (why std::map then flat array; why
    GPUs are NOT on the hot path; how you avoid look-ahead bias in backtests).
    Showing you know WHY is what gets you past interviews.

7F. Resume bullet templates (fill in YOUR numbers):
  - "Built a low-latency HFT system in C++20 (order book, matching engine,
     market-data feed handler, strategy + risk engine) achieving p99 tick-to-
     trade latency of <X us>."
  - "Designed lock-free SPSC/MPSC ring buffers and a custom memory pool,
     eliminating hot-path allocations and cutting p99 latency by <Z%>."
  - "Implemented a GPU-accelerated backtester (CUDA) that swept <N> strategy
     configurations <100x> faster than the CPU baseline."
  - "Trained and deployed an order-book-imbalance ML signal (ONNX Runtime in
     C++) and backtested it against baseline strategies."

7G. Talk about it well: be ready to whiteboard the order book, explain your
  latency measurements, and discuss what you'd do with more time. Depth wins.
