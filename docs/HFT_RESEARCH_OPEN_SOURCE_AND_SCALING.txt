================================================================================
 3. GUSTGRID: REVIEW AND RATING
================================================================================

Repository: github.com/josephHelfenbein/GustGrid
I cloned it and read the source. I did not build or run it (it needs an
NVIDIA GPU), so the rating is based on the code, the README and the history.

What it is
  A real-time airflow and heat simulation of a PC case. A 64 x 256 x 128
  voxel grid (2.1 million cells) is simulated on the GPU with CUDA and
  drawn with OpenGL. The user toggles fans and the GPU and watches the
  air speed, pressure and temperature fields change.

Facts
  - 71 commits by one author. Core work ran from 25 May to 23 June 2025,
    about four weeks. 27 stars, 3 forks.
  - About 2,950 lines of the author's own code: 1,292 lines of CUDA
    (fluidSimulator.cu), 1,148 lines of renderer (renderer.cpp), 151
    lines of scene setup, about 320 lines of GLSL in eight shaders.
    main.cpp is five lines.
  - Third-party: GLFW, GLM, FreeType, stb, glad, an OBJ loader.
  - No tests, no CI workflow, no benchmark numbers.

What is strong
  - 13 CUDA kernels covering divergence, Jacobi pressure solve, gradient
    subtraction, boundary enforcement, forward advection, convective and
    conductive heat transfer, and fan forces.
  - The Jacobi kernel loads each 8x8x8 block plus a one-cell halo into
    shared memory (a 10x10x10 tile) before iterating. That is the correct
    way to cut global-memory reads in a stencil and shows real GPU skill.
  - Forward advection scatters with atomicAdd and then normalises, a
    harder design than the usual backward semi-Lagrangian step.
  - The simulation writes straight into OpenGL 3D textures through
    CUDA-OpenGL interop, so no data returns to the CPU per frame.
  - The residual reduction runs on the GPU. Constants live in CUDA constant
    memory. Kernels use __restrict__ and fused multiply-add intrinsics.
  - The renderer has PBR shading with normal, metallic and roughness maps,
    a ray-marched volume shader, text rendering, and a hand-built UI with
    checkboxes and sliders. A compute shader reads temperatures back.
  - It builds on Linux and Windows, has a clear README with a video, and
    it is finished. The commit history shows steady optimisation passes,
    for example merging kernels, speeding up the ray marcher and moving
    the residual sum from the CPU to a GPU kernel.

What is weak
  - Numerical rigor. The pressure solve runs a fixed maximum of 8 Jacobi
    iterations and resets pressure to zero every step. One Jacobi sweep
    moves information one cell, so on a grid this size the velocity field
    is only roughly divergence-free. The velocity update is full of
    hand-tuned clamps, damping factors and thresholds. The result looks
    plausible but is not validated against any known flow.
  - A real bug that a test would have caught: in velocityUpdateKernel the
    Y-direction temperature gradient is assigned to gradX (line 1174), so
    gradY is always zero and the X value is overwritten.
  - Code structure. Scene state, GPU pointers and UI state are global
    variables. renderer.cpp is one 1,148-line file. Shader sources are
    loaded with raw malloc. The simulator is reached through singletons.
  - cudaDeviceSynchronize is called after nearly every kernel launch (14
    call sites), which is unnecessary on a single stream.
  - No tests of any kind, no CI, no frame-time or throughput numbers.
  - The README says MIT; the LICENSE file is Apache 2.0.

Rating scale used here
  100  production-grade open source written by specialists (QuantLib, Aeron)
   85  would stand out among professional engineers' personal work
   70  strong undergraduate portfolio project
   50  typical finished course or side project

Skill categories weigh more than process categories because you asked
about skill level.)

  model, and a stranger who opens your repository today sees an empty
  README. The gap between the two projects is presentation and completion,
  not difficulty.

  The two largest gaps are the 20-weight skill row (no lock-free code, no
  measured optimisation, strings and maps on the hot path) and the demo
  row. Both are fixable without new components.

A low-latency project is judged differently from a graphics project. It has
to prove three things: that it is correct, how fast it is and how you know,
and what happens when something fails. A project that proves those on real
data is rarer than a good demo.

What the top of the personal-project range looks like right now
  - ASherjil/abt-t2t (C++). ITCH 5.0 feed handler and OUCH order entry
    over Solarflare ef_vi kernel bypass, with tick-to-trade measured by NIC
    hardware timestamps over a full Nasdaq trading day. Its README reports
    about 5.4 million samples with the worst at roughly 3.2 microseconds.
    This is the strongest public personal HFT project I found. It needs
    two specialist network cards, so treat it as the ceiling, not the plan.
  - KareemJandali/itchbook (C++20). ITCH 5.0 book reconstruction, matching
    engine and a queue-aware backtester.
  - chronoxor/CppTrader (C++). Matching engine, order book and ITCH
    handler. READMEs of its forks report a sample Nasdaq day of about
    268-283 million ITCH messages parsed at roughly 100-117 ns per message.
    Reproduce this on your own machine and use it as your baseline.
  Read all three before you design the ITCH stage. They show what a
  reviewer will compare you against.

The six goals that put this project at 85-90
  GOAL 1  Visible.  README with architecture diagram, build commands, a
      status table and a 60-90 second demo video. Green CI badge.
      [A01 A02 F05]
  GOAL 2  Correct.  Fixed-point prices end to end. A simple reference
      matcher and a million seeded random operations compared against the
      fast one. Fuzzed decoders. Sanitizers in CI. [A03 A05 A06 C01 C02]
  GOAL 3  Real data.  A Nasdaq TotalView-ITCH 5.0 decoder that rebuilds
      every book for a full trading day, with messages per second,
      nanoseconds per message and memory published next to the CppTrader
      baseline. [D01 D02 D05]
  GOAL 4  Measured.  p50 / p99 / p99.9 / max with a written methodology,
      and one optimisation told as a case study: std::map<double> price
      levels replaced by a tick-indexed array, and O(depth) cancel replaced
      by an intrusive doubly linked list, with before and after numbers
      and a flame graph. [C03 C04 E02 E04]
  GOAL 5  Systems depth.  An SPSC ring buffer you wrote, tested under
      ThreadSanitizer and benchmarked against rigtorp/SPSCQueue,
      boost::lockfree::spsc_queue and max0x7ba/atomic_queue. Pinned
      threads. One networking experiment with numbers. [E05 I04 I05]
  GOAL 6  Demonstrable.  A live order-book depth heatmap driven by the
      real ITCH replay, with a fault injected on screen and the engine
      halting and recovering. This is your answer to GustGrid's video.
      [F03 F04]

  Stretch to 90+: the latency-sensitivity study [I01], or one merged pull
  request in each of two projects from section 5.

HOW TO CONTRIBUTE SO THAT IT COUNTS
--------------------------------------------------------------------------------
  - Pick two projects, not ten. My recommendation: QuantLib plus quill.
    Swap quill for BlazingMQ if you prefer distributed systems.
  - Before anything else, clone it, build it and run its full test suite.
    That alone takes a day on a large project and teaches you its layout.
  - Make the first pull request small: a failing test for a real bug, a
    documentation fix you needed yourself, a missing benchmark. Read
    CONTRIBUTING and comment on the issue before you start work.
  - Realistic pace: one merged pull request a month.
  - Budget: about one fifth of your project time. A merged PR is strong
    evidence because a stranger reviewed your C++, but it does not replace
    finishing your own engine.
  - On the resume: "Contributed <what> to <project> (merged PR #N)", with
    the link. Never list a project you only opened an issue on.


================================================================================
 6. SCALING TO PROFESSIONAL / PRODUCTION LEVEL
    Ideas, todos and concepts. Nothing here is implemented.
================================================================================

"Production level" means five properties, in this order of importance:
  1. Correct     every state change is defined, tested and reproducible
  2. Observable  you can say what it is doing and how fast, with evidence
  3. Recoverable it fails safely and comes back to a known state
  4. Fast        predictable tail latency, not just a good median
  5. Operable    someone else can build, run, configure and debug it

--------------------------------------------------------------------------------
6.1 ARCHITECTURE
--------------------------------------------------------------------------------
Concept: single-writer, deterministic core. One thread owns the book,
strategy, risk and order state. Inputs arrive as a single ordered stream of
events; outputs leave as events. No locks inside. The EDX exchange described
in your PRODUCTION_REFERENCES.md works this way, because it makes replay,
testing and recovery possible.

  [ ] Define one sequenced input event type and make every component
      consume it. The same binary must run live, in replay and in tests.
      [J1 J5 E7]
  [ ] Journal every input event before it is applied. Recovery is: load
      the last snapshot, replay the journal. [H01 D06]
  [ ] Thread layout: feed thread -> SPSC -> core thread -> SPSC -> gateway
      thread, plus a low-priority thread for logging and metrics. Write the
      layout down with core numbers before coding it. [B3 E05]
  [ ] Delete the std::mutex from OrderManager by giving the OMS to the
      core thread. A lock is only needed where two threads share state,
      and after this change none do. [B4]
  [ ] NEW  Publish top-of-book to other processes through a seqlock in
      shared memory, so a dashboard or a second strategy can read it
      without ever blocking the core.
  [ ] NEW  Split the repository into libraries with one-way dependencies
      (common -> marketdata -> book -> strategy/risk -> execution -> apps)
      and make CMake enforce it. Today everything is one "hft" target.

--------------------------------------------------------------------------------
6.2 DATA STRUCTURES AND MEMORY
--------------------------------------------------------------------------------
  [ ] Finish fixed-point prices everywhere. Integer ticks as keys. [A03]
  [ ] Replace `long` with int32_t / int64_t / uint32_t chosen on purpose,
      and static_assert the size of every wire and storage struct. [A04]
  [ ] Price levels: replace std::map<double> with a structure chosen from
      measurement. Candidates: array indexed by tick offset from a moving
      base; sorted flat vector with the best price at the back; small
      B-tree. Benchmark each on real ITCH data, dense and sparse. [B8]
  [ ] Orders within a level: intrusive doubly linked list so cancel is an
      O(1) unlink given the order pointer. [E02]
  [ ] Order-id lookup: open-addressing flat hash map with preallocated
      capacity, or a direct array if ids are dense. Compare against
      std::unordered_map and unordered_dense. [E02]
  [ ] Symbols as small integer ids resolved once at startup. No
      std::string in any event, order or report. Report type as an enum.
      [B5 E03]
  [ ] Execution reports written into a caller-provided fixed buffer or a
      bounded sink, never a returned std::vector. [B6 E03]
  [ ] Prefault and lock all pools at startup (mlockall on Linux), then try
      huge pages and measure the difference. [I04]
  [ ] Decide alignas(64) per struct from access pattern. It prevents false
      sharing between threads but makes a list walk touch one cache line
      per order. For single-threaded structures, packed is usually faster.
      [E04]
  [ ] NEW  Zero-allocation proof: replace global operator new in a test
      build with a counter that aborts after warm-up, and run every hot
      path workload under it. This turns "no allocation" from a claim
      into a test.

--------------------------------------------------------------------------------
6.3 CONCURRENCY
--------------------------------------------------------------------------------
  [ ] Write your own bounded SPSC ring: power-of-two capacity, head and
      tail on separate cache lines, cached copies of the opposite index,
      acquire/release ordering you can justify line by line. [B1 E05]
  [ ] Test it: wraparound, full, empty, shutdown, 100 million items under
      ThreadSanitizer, producer and consumer pinned to different cores.
  [ ] Benchmark it against three libraries (section 5, item 4) and publish
      throughput and latency on the same machine.
  [ ] MPSC queue only for fan-in to the logger. [B2]
  [ ] Seqlock for "latest value" data such as top-of-book and risk limits.
  [ ] NEW  Write a one-page memory-ordering note for each concurrent
      structure: what each atomic protects, why each ordering is enough,
      and what breaks if it is weakened. Interviewers ask for this.

--------------------------------------------------------------------------------
6.4 MARKET DATA AND NETWORKING
--------------------------------------------------------------------------------
  [ ] Nasdaq TotalView-ITCH 5.0 decoder. Decode in place from the buffer
      with explicit big-endian reads. Handle every message type or count
      what you skip. [D01]
  [ ] Rebuild all books for a full day; verify against hand-checked
      fixtures and against CppTrader's output. [D02 G6]
  [ ] NEW  MoldUDP64 framing with sequence numbers, which is how ITCH is
      carried on the wire. Detect gaps; request retransmission; mark the
      book stale until continuity returns. [D3 F01]
  [ ] A/B feed arbitration: two identical streams, take whichever packet
      arrives first, drop the duplicate. [D2]
  [ ] NEW  OUCH 5.0 order entry over SoupBinTCP as a second, binary
      gateway beside FIX. OUCH is Nasdaq's binary order-entry protocol;
      FIX is the slower, more general path.
  [ ] NEW  pcap replay: record your simulator's traffic to a capture file
      and replay it at real or accelerated speed. This gives a repeatable
      network benchmark without an exchange.
  [ ] Socket ladder, each step measured against the last on identical
      traffic: blocking sockets -> epoll -> busy polling -> io_uring ->
      AF_XDP. Report the mode actually achieved. [D5 D6 I05]

6.9 MODERN C++ UPGRADES THAT EARN THEIR PLACE
--------------------------------------------------------------------------------
Move to C++20 (C++23 where both GCC and MSVC support the feature) only for
features that remove a real problem. [H4]

  [ ] std::span for every buffer boundary; std::string_view at the edges.

================================================================================
 7. C++ MASTERY PATH FOR A QUANT DEVELOPER
================================================================================

Reaching a high level in C++ comes from three habits more than from any
book: build the primitive yourself, measure it against the library version,
and read the library's source to see why it differs.

--------------------------------------------------------------------------------
7.1 SKILL LADDER, WITH A CHECK FROM YOUR OWN CODE AT EACH LEVEL
--------------------------------------------------------------------------------
L1  Language core: value categories, move semantics, RAII, rule of zero,
    const-correctness, undefined behaviour.
    Check: explain exactly what is copied and allocated when submitOrder
    returns std::vector<MatchExecReport>.

L2  Memory and hardware: cache lines, alignment, TLB, branch prediction,
    allocators, object lifetime.
    Check: MemoryPool maps a T* back to its Slot with reinterpret_cast. Say
    why that is valid, what the static_assert guarantees, and what
    std::launder is for.

L3  Concurrency: the memory model, atomics and orderings, false sharing,
    SPSC / MPSC queues, seqlocks, the ABA problem.
    Check: nextId_ in OrderManager is atomic and everything else is under a
    mutex. Which ordering does nextId_ need, and why is it atomic at all?

L4  Generic and compile-time programming: templates, concepts, CRTP,
    constexpr, type erasure and its cost.
    Check: replace the std::function callbacks in OrderManager with a
    template parameter and show the difference in the generated assembly.

L5  Toolchain: compiler flags, sanitizers, perf, flame graphs, Compiler
    Explorer, llvm-mca, PGO and LTO.
    Check: explain why `volatile auto reports` in latency_bench changes
    what is measured, and what benchmark::DoNotOptimize does instead.

L6  Operating system and network: syscalls, scheduling, page faults,
    sockets, epoll, io_uring, NUMA, kernel bypass.
    Check: list every reason one sample in your histogram could be 100
    microseconds when the median is under one.

L7  Domain: market microstructure, order types, exchange protocols, market
    making, risk, transaction costs.
    Check: explain why a limit IOC must not trade through its limit price,
    and what your engine does today [A05].

--------------------------------------------------------------------------------
7.2 BUILD-IT-YOURSELF EXERCISES (each maps to a part of the engine)
--------------------------------------------------------------------------------
  1. SPSC ring buffer           compare: rigtorp, boost, folly, atomic_queue
  2. Open-addressing hash map   compare: std::unordered_map, unordered_dense
  3. Arena / pool allocator     compare: your MemoryPool, std::pmr
  4. Fixed-point decimal type   compare: double; test overflow and rounding
  5. Small inline vector        compare: std::vector, boost small_vector
  6. Non-allocating callable    compare: std::function
  7. Seqlock                    compare: std::mutex, std::atomic<struct>
  8. Flat order book            compare: your std::map version on ITCH data
  9. Latency histogram          compare: HdrHistogram_c
 10. ITCH decoder               compare: CppTrader's handler
For each: write it, test it under sanitizers, benchmark both, write half a
page on why the numbers differ. Ten of these is a serious C++ education and
most of them go straight into the project.

The project covers C++ and systems design. It does not cover the rest:

    cache behaviour. Section 7.1's checks are practice for this.
